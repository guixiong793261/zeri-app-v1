## 〇、结论摘要（先看这段）

1. **性能不是瓶颈**：单次 `calculate_score` 实测 2.4～6.1 ms；单日 12 时辰实评 32 ms（入宅）/ 73 ms（嫁娶）；30 天 × 12 时辰 = **1.0 s / 2.2 s**，90 天 = **2.9 s / 6.6 s**。用户要求"1～3 秒"在 30 天范围可满足，90 天需两级筛选。
2. **不需要新算法核心**：现有扫描已经在做"每日 12 时辰实评择优"（`_rescan_best_hour`），反推引擎本质是**把现有打分函数换成搜索策略**，分数完全复用 `calculate_score`，可保证"反推结果 = 手点该日看到的分数"。
3. **真正的难点在组合与呈现，不在算力**：①"发轿→迎娶→拜堂"这类**同日动作序列**目前无独立事项口径（软件只有 16 个事项，无动作级模型）；②多日组局的约束定义与 UI 呈现方式需要您拍板。
4. **建议分期**：P1 单事项 Top-N（30 天，含粗筛）→ P2 热力日历＋时间轴 → P3 组局（同日动作序列 / 多日组合）。

## 一、输入维度对齐

### 1.1 现状可复用的输入面

| 维度 | 现状 | 反推引擎需要的增量 |
|------|------|-------------------|
| 事主 | GUI 已有事主增删（姓名/性别/角色/生肖/八字/喜用神），`owners` 列表直通评分器 | 支持 1～6 人（实测 0/1/2/4 人事主成本差 <0.5 ms，无性能压力）；增加"权重/主事人"标记（见 §3.3） |
| 事项 | `UI_EVENTS` 16 项（嫁娶/订婚/纳采/修造/动土/拆舍/入宅/开业/出行/安床/作灶/移徙/入学/求医/签约/安葬），别名归一已有唯一注册表 | 组局需新增"动作"概念：动作 = 事项 + 先后顺序 + 可接受时辰窗（**当前不存在**） |
| 范围 | 已有开始/结束日期 + 进度条 + 任意跨度扫描 | 改为"起始日 + 未来 N 天"（7/30/90/180 预设），并显示预计耗时 |
| 约束 | 山向/兼向、宅型、灶向灶位、床位朝向、作灶模式、择日模式（飞星/正五行） | 反推需把这些作为"固定上下文"一次性确定，搜索期间不变 |
| 事主冲避 | 规则层已含年柱/日柱冲事主、家长一票否决等 | 无需改造，随 `owners` 自动生效 |

### 1.2 新增输入（建议最小集）

- **搜索范围**：起始日 + N 天（默认 30）。
- **结果数量**：Top N（默认 10 日；组局另算）。
- **收录口径**（单选，须拍板）：
  - `仅吉日`：沿用现有过滤链（score>0、等级无"凶"、无"忌本事项"、无硬否决）；
  - `吉日+慎用`：额外收入"有扣分但无否决"的日，标黄；
  - `含否决`：仅用于诊断（如坐山犯年煞导致 0 结果）。
- **可选开关**：排除周末/法定假期（纯日历过滤，不涉术数）、"每 N 天最多 M 个吉日"（防止连续推荐）。

### 1.3 明确不做（本引擎范围外）

- 不新增神煞/不修改任何分值（分值与否决完全来自现有评分器）。
- 不生成"另一套分数"（避免出现"反推推荐 88 分、点开详情 76 分"的口径分裂）。
- 不做流年/流月大运选期（属"择年择月"另一形态，另行立项）。

## 二、算法与性能推演

### 2.1 实测数据（本机，Python 3，2026 全年抽样；owners=[]/1/2/4 人）

| 测量项 | 中位数 |
|--------|--------|
| `calculate_sizhu` 单次 | 0.04 ms |
| `calculate_score` 入宅 | 2.4～3.0 ms |
| `calculate_score` 修造 | 3.0～3.3 ms |
| `calculate_score` 开业 | 3.1～3.7 ms |
| `calculate_score` 嫁娶（最重） | 5.6～6.1 ms |
| **单日 12 时辰实评（入宅）** | **32 ms** |
| **单日 12 时辰实评（嫁娶）** | **73 ms** |
| 粗筛通道·神煞检查器（单时辰） | 0.2～0.8 ms |
| 粗筛通道·规则层（单时辰） | 0.8～1.3 ms |

**推算**（线性外推，已含年月日柱复用缓存的前提）：

| 范围 | 入宅 12h | 嫁娶 12h | 说明 |
|------|---------|---------|------|
| 30 天 | **1.0 s** | **2.2 s** | 满足 1～3 s 目标 |
| 90 天 | **2.9 s** | **6.6 s** | 嫁娶超标，需两级筛选 |
| 365 天 | 11.8 s | 26.7 s | 必须后台线程 + 粗筛 |

> 关键事实：现有 GUI 扫描**已经是**每日 12 时辰实评（`_rescan_best_hour`，2026-10-02 方向 A/D 已做年月日柱复用与结果缓存）。因此"反推 90 天"的算力成本 ≈ "现有扫描 90 天"，不是新增量级；真正的新增只有**排序/组合/呈现**。

### 2.2 两级筛选（推荐方案）

```
Stage A  日级粗筛（全范围）
  ├─ 逐日：神煞检查器 + 规则层（否决/硬忌）      ≈ 1.0～2.0 ms/时辰 → 12～24 ms/日
  ├─ 交节修正：逐时辰算年月日柱（保留现有"交节后月柱切换"口径）
  └─ 输出：否决日集合 + 每日子分数（可用午时完整分作代理）
Stage B  时级精算（仅存活日/Top K 日）
  ├─ 12 时辰 calculate_score 全量实评（复用 _rescan 排序键）
  └─ 输出：每日最优时辰 + 该时辰完整评分
Stage C  排序与去重
  ├─ 排序键：否决数 → 总分 → 事主喜用神匹配 → 吉神命中（与 _rescan 同口径扩展）
  └─ 去重：同日只留最优时辰；连续吉日按"间隔约束"稀疏化
```

**耗时预估（30 天 · 嫁娶 · 2 事主）**：Stage A ≈ 0.3～0.7 s；存活日约 40%～60% → Stage B 12～18 天 × 73 ms ≈ 0.9～1.3 s；合计 **1.2～2.0 s**，满足目标。90 天用同一流程约 **4～5 s**（可接受，需进度条/后台线程）。

**降级策略**：若 Stage B 存活日过多，先按"日级代理分"取 Top K（K=20）再做 12 时辰精算，确保 ≤3 s。

### 2.3 必须遵守的三条性能/口径纪律

1. **交节时刻**：同一天内年月日柱并非恒定（2026-10-03 已修过"酉/戌时月柱被压回上月"的 98→83 事故）。反推**禁止**只算午时年月日柱后套用到全 12 时辰，必须逐时辰取权威值。
2. **排序键同源**：反推的"最优时辰"必须与手动扫描的 `_rescan_best_hour` 排序键**完全一致**（否决数含分金重罚 → 扣分金后总分 → 无杀师 → 分金档 → 五行原始分），否则会出现"自动推荐 vs 手动扫描"两套结论。
3. **否决口径同源**：粗筛的"剔除"必须复用现有过滤链（`veto_reasons`、score>0、等级无"凶"、`忌{事项}`、`不宜{事项}`、严重凶煞关键词），不得另设一套黑名单。

### 2.4 线程与交互

- 搜索在**后台线程**执行（现有扫描在 GUI 主线程 + `update_idletasks`，90 天会明显卡顿）。
- 进度回调：阶段权重 A 30% / B 60% / C 10%；显示"已筛 X 天，存活 Y 天，精算中 Z/Y"。
- 结果流式：每算完一天即入堆，可"边算边看 Top 5"；支持中断。

## 三、组合与排序逻辑

### 3.1 三类"组局"必须分开建模（当前只有第①类有基础）

| 类型 | 示例 | 现有能力 | 需要新增 |
|------|------|---------|---------|
| ① 单日多动作（时序） | 发轿 07:00 → 迎娶 09:00 → 拜堂 11:00 | **无**（软件无"发轿/迎娶/拜堂"事项口径，仅红纸帖文案出现） | 动作→事项映射表、时辰窗、相邻动作约束 |
| ② 多日多事项（无关或弱关联） | 入宅（10/20）＋请客（10/22）＋安床（10/25） | 可分别评分，无组合搜索 | 组合筛选、间隔约束、顺序约束 |
| ③ 多日同事项（分批） | 连续三日宴客 | 无 | 去重与节奏约束（低优先） |

> **重要结论**：用户举例的"发轿/迎娶/拜堂"不是现成事项，**不能直接丢给 `calculate_score`**。必须先做《动作级事项映射》立项（每个动作映射到已有事项或明确"复用嫁娶口径"），否则组局会出现"三个动作都按嫁娶打同一分"的假精度。

### 3.2 同日时序（类型①）算法

1. 每个动作 → 事项 + 允许时辰窗（如发轿限卯～巳、拜堂限巳～未，具体待典据/民俗拍板）。
2. 对当日 12 时辰逐一评分（每动作一份 12 时辰矩阵，成本 = 动作数 × 73 ms）。
3. 用**时间轴 DP**：`dp[i][h] = max(dp[i-1][h'] + w_i·score_i(h))`，约束 `h > h'` 且相邻动作不冲（如发轿时支与迎娶时支六冲则禁）。
4. 输出"最优时间轴"，并给出次优方案 2～3 条，供人工取舍。

### 3.3 多日组合（类型②）算法

- 事实前提：不同日之间除"事主年命、月令、节气"外**无相互术数作用**，因此组合可分解为"选 N 天"。
- 候选集：每个事项各取 Top M（M=8～10）→ 组合规模 ≤ 10³，可全枚举；物品更多时用 **beam search（宽度 20）**。
- 硬约束（须拍板）：先后顺序（入宅→安床通常入宅在前）、最小间隔（如 ≥2 天）、同月上限、不得与事主冲日。
- 目标函数：`Σ日分 + λ·事主喜用神匹配 + μ·吉神稀有度 − ν·否决/慎用惩罚`。

### 3.4 "分值最高" vs "吉神最匹配"的权衡

建议**两级排序**，不做单值混合（避免"玄学权重"不可解释）：

1. **第一级（硬）**：否决数 = 0 → 总分降序。
2. **第二级（软）**，同分或分差 ≤3 分内时依次比较：
   - 事主喜用神命中（`score_details['喜用神得分']` 与各事主用神）；
   - 关键吉神命中（天德/月德/天赦/天愿等"主锚级"）；
   - 凶煞数量与最重凶煞力度；
   - 与事主生肖六合的个数。
3. UI 上把"为什么排第一"写成一句话（如"天德＋月德＋喜用神水，无否决"），不暴露黑箱权重。

> 纪律建议：**任何"权重 λ/μ/ν"都先以固定常量落表并写入文档**，不做隐式调参；若您希望"按事项微调权重"，须逐事项拍板（如嫁娶重吉神、修造重山向）。

## 四、UI 呈现形式（三选一还是三层叠加）

建议**三层叠加**（同一份搜索结果，三种视图，不重复计算）：

### 4.1 第一层：吉日热力日历（总览）

- 月历格子：颜色 = 该日**最优时辰总分**分档（≥90 深红大吉 / 75-89 红 / 60-74 黄慎用 / <60 灰 / 0 或否决 黑）。
- 格子角标：最优时辰地支（如"辰"）；悬浮提示一句主因。
- 交互：点击格子 → 展开当日 12 时辰条形图 → 再点时辰 → 打开现有"日课详情"。
- 现有代码无热力图组件，需新建（`tkinter Canvas` 或 `matplotlib`，项目已有 matplotlib 依赖）。

### 4.2 第二层：Top-N 吉日列表（决策）

列：排名 / 日期（公历+农历）/ 最优时辰 / 总分 / 等级 / 关键吉神 / 否决或慎用原因 / 操作（查看详情·生成红纸帖·加入方案）。

- 与现有结果表风格一致（复用列渲染与详情跳转）。
- 支持"加入方案"把候选日放入一个"择日方案篮"，供组局阶段使用。

### 4.3 第三层：最优时间轴（执行）

- 仅组局模式出现：横向时间轴卡片 `10/20 07:00 发轿（88 分，天德）→ 09:00 迎娶（91 分）→ 11:00 拜堂（85 分）`。
- 每个节点可展开依据（吉神/忌项/否决），并可一键生成红纸帖（复用现有 `择日贴.py`）。
- 次优方案并列 2～3 条，标注与最优的差异点。

### 4.4 不建议的做法

- **只给 Top-10 列表**：无法回答"这个月哪天能办"，用户仍需逐日点开。
- **只给热力图**：无法给出时辰级执行方案。
- **把"慎用日"混进 Top-10 而不标色**：会诱导误用（本项目一贯强调"忌项可见"）。

## 五、架构草案（模块划分，不改评分器）

```
modules/
  反推引擎.py            # 新增：搜索编排（粗筛→精算→排序），只调用 calculate_score
  组局优化.py            # 新增：动作序列 DP / 多日 beam search（P3）

GUI（主程序.py）
  新增"精准择时"页签：输入区（事主/事项/范围/口径）＋ 三层视图 ＋ 后台线程与进度
```

**API 草案（伪签名，非实现）**：

```python
search_best(event, owners, start, span_days, *, top_n=10,
            mode='吉日',           # 吉日 / 吉日+慎用 / 含否决
            context=None,          # 山向/宅型/灶向/床位/择日模式
            constraints=None,      # 间隔/顺序/周末排除
            progress=None)         # 回调(phase, done, total)
# → {'days': [...], 'vetoed': [...], 'meta': {'elapsed', 'scanned', 'survived'}}

search_group(plans, owners, start, span_days, *, mode='时序'|'多日', ...)
# → {'best': {...}, 'alternatives': [..2], 'meta': {...}}
```

**关键设计约束**：
- `反推引擎` 只做编排与排序，**不计算任何分数**（分数一律来自 `calculate_score`）。
- 排序键与 `_rescan_best_hour` 抽成**公共函数**（建议 `rank_key(result)` 单点），反推/手动扫描/详情注入三处共用，防止口径漂移。
- 搜索状态不可变快照（输入指纹：事项 + owners + 山向 + 择日模式），防止"改事主后旧结果还在"。

## 六、风险清单

| # | 风险 | 影响 | 处置建议 |
|---|------|------|---------|

## 七、需要您拍板的问题（8 项）

1. **范围上限**：30/90/180 三档是否足够？是否允许 365？
2. **收录口径**：Top 列表默认"仅吉日"，"慎用"是否作为第二区段展示？
3. **Top N**：默认 10 日是否合适？组局是否默认给 3 套方案（最优+2 备选）？
4. **组局优先级**：P1 先做单事项 Top-N，还是直接上"同日动作时序"？（后者需先做动作映射立项）
5. **动作映射口径**："发轿/迎娶/拜堂"按嫁娶同一事项打分，还是要各自独立评分口径？
6. **间隔约束**：多日组合是否强制最小间隔（如 2 天）与先后顺序？
7. **吉神匹配权重**：同分（或 ≤3 分差）时是否按"喜用神命中 ＞ 主锚吉神 ＞ 凶煞数量"排序？
8. **结果联动**：选中日是否直接生成红纸帖/导出方案（复用现有 `择日贴.py`）？

## 八、建议分期（拍板后细化，不在本草案内动工）

| 期 | 内容 | 交付判定 |
|----|------|---------|
| P1 | 单事项 Top-N（30 天，粗筛+精算+后台线程） | 结果与手动逐日扫描**逐分对拍一致**；30 天 ≤3 s |
| P2 | 热力日历 + 12 时辰条 + Top-10 列表（三层视图联动） | 点选热力格与列表结果一致；详情跳转可用 |
| P3 | 组局（同日时序 DP → 多日 beam search） | 时间轴可输出红纸帖；约束可配置可回放 |
| P4 | 性能与体验收口（180 天、缓存、中断、进度） | 180 天 ≤8 s；内存稳定 |
