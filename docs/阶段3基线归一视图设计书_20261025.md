### 2.3 嫁娶链的"零分墙"

- 嫁娶 **score==0 的天数 266/365（72.9%）**，其中 raw_score<0 被 max(0,·) 截断 111 天，raw 恰为 0 的 155 天。
- 即嫁娶总分公式中 marriage_result['score'] 一项在近四分之三天里**归零**，总分几乎只剩 喜用神+月令+太阳太阴 三个附属项，量级天然在 0–40 区间——再叠加 T2 的"五行分<60 判凶"底线（嫁娶的"五行分"=嫁娶评分本身），形成**双通道同时判凶**。

### 2.4 根因分析：为什么两条链容忍度完全不同

1. **分值尺度不同源**：通用链基础分 100，嫁娶链基础分 60。同一阈值表（105/100/85/75/60）对基础 60 的链而言，上吉线 105 要求净加成 +45 以上，而嫁娶专有吉神单项多为 +8~+30，叠加难以企及。
2. **否决密度不同源**：嫁娶链承载事主专属否决（冲新娘本命、阴胎、阳气、本命三煞、夫星受耗等），2026 对本样本新人否决 264 天（72.3%）；入宅否决仅 32 天（8.8%）。
3. **负分截断不对称**：嫁娶 raw<0 被截为 0（T6），通用链不截断（入宅实测最低 -121）。截断使嫁娶低分日全部堆叠在 0 分，抹平了"小凶"与"大凶"的区分度。
4. **飞星封顶错位**：修造 feixing 模式 clamp 到 100，永不可达上吉（105）——同一场景正五行模式可达 247。这是"不同通道分值截断差异"的具体实证。

## 三、归一化架构设计（三个候选方案）

### 方案 A：归一化展示层（推荐）

**不动任何计分本体**，在 `_get_level` 前插入一层"管线刻度归一化"：

```
raw_total（各管线原分，保留展示与排序）
   │
   ▼  normalize(event_type, raw_total)  —— 按管线基线参数线性映射
normalized_score = (raw_total - BASE[event]) * K[event] + 100
   │
   ▼  _get_level(normalized_score)      —— 唯一阈值表 105/100/85/75/60
level
```

- BASE/K 为**管线基线常数**（如嫁娶 BASE=60、K≈100/60 待定；通用 BASE=100、K=1 恒等不动）。
- 通用链 K=1、BASE=100 ⇒ 映射恒等，**通用/修造/入宅等 10 事项等级零变化**；
- 嫁娶链重标定后，均值 13.16 → 映射到与通用链同量级，上吉/大吉档重新可达；
- 排序键改用 normalized_score（同管线内单调不变 ⇒ **管线内排序零扰动**；跨管线排序原本就不可比）。

优点：计分公式、神煞分值表、一票否决、两级封顶全部不动；所有改动集中在单一纯函数，可逆、可关闭（开关参数）。
缺点：BASE/K 的取值是**新拍板项**，需要分布数据支撑（本报告 §二已给出 2026 实测）。

### 方案 B：直接改嫁娶计分基线（重标定计分本体）

把嫁娶基础分 60→100、或调整专有吉神分值使分布对齐，然后继续共用 _get_level。

- 缺点致命：违反"计分冻结"体系——4015 条基线、全部嫁娶 verify（福星 fd0f32d、verify_hongsha 分值锁、verify_bazhuan -12 等数十个断言值）全部漂移；§176 刚完成的福星接入也要重冻。**不建议**。

### 方案 C：仅清理死代码 + 统一文案档

删除 D1 死映射、把 D2/D3 文案档对齐 T1。治标：分布错位原样保留，嫁娶 93.7% 判凶不变。可作为方案 A 的**伴随批次**执行。

### 推荐组合

**A（主体）+ C（伴随清理）+ 飞星封顶专项（独立拍板，见 §四 R3）**。
