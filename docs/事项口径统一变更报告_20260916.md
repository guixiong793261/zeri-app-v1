## 一、背景与问题

同一神煞/规则在软件的三条链路中各自硬编码，导致口径不一致：

1. **择日批选**（`主程序.py` 扫日打分）
2. **日课评分**（`modules/评分器.py` / `modules/日课评分系统.py` 手动评价）
3. **详情展示**（主程序双击结果行的日课详情、时辰吉凶表）

具体表现：
- 14 个事项的别名（装修/破土/拆除/移徙/搬家等）在各处分发逻辑不同；
- 同名神煞在不同事项下分值不同（如「驿马」在多数事项 +10，在动土/入宅/移徙却为 +12），且分值散落在 10 余个 checker 文件的字面量中；
- 推荐时柱的时辰项分值（如「日破时」）与日课神煞分值各写一套；
- 玄空飞星事项、嫁娶利月、作灶半权重等"评分画像开关"在评分器中多处硬编码且漏列（如「安葬」在飞星事项中两处漏列）；
- 正常择日与条件择日两条结果渲染链路列格式不同。

## 二、架构变更：建立唯一事实源

### 2.1 新建 `modules/事项标准.py`（Single Source of Truth）

所有事项口径只在该文件登记一次：

| 登记内容 | 说明 |
|---|---|
| `UI_EVENTS` / `EVENT_ALIASES` | 14 个规范事项与全部别名；`canonical_event()` 别名→规范名 |
| 事项分组 frozenset | `MARRIAGE_EVENTS`、`FEIXING_EVENTS`、`SHAN_UI_EVENTS` 等，均经别名自动展开 |
| `RULE_CHECKER_CLASSES` / `SHENSHA_CHECKER_CLASSES` | 规则/神煞检查器"模块路径+类名"懒加载派发表 |
| `EVENT_PROFILES` | 各事项评分画像（嫁娶/山向中心/飞星/利月/作灶半权/修造扩展等开关） |
| `SHENSHA_SCORES` | 神煞分值单一表：1413 条运行时观测真值 + `('*', 名)` 通配兜底 |

```
(规范事项, 神煞名)  →  ('*', 神煞名) 通配  →  调用处默认值
```

## 三、分值调整依据

### 3.1 方法论：运行时观测真值 + 众数对齐（关键纪律）

**不能直接改源码字面量**。因同名神煞存在继承/去重机制，源码字面量常常不等于运行时生效值（例如作灶「四离日」源码写 -30、实际生效 -35）。改造前先通过运行时观测脚本（`C:\Temp\_observe_shensha_scores.py`）对 14 事项全量评分，得到每个神煞的**实际生效分值**，再据此决策。

通用神煞的统一值取**多数事项的主流值（众数）**：典籍对神煞只定性质与轻重层级、不规定软件具体分数，故分值以"多数事项原本就在用的值"为准，最大程度减少行为漂移；少数事项的偏离值向众数收敛。典籍来源仅用于确认神煞性质与轻重方向（吉神加分、凶煞扣分、重煞多扣）。

### 3.3 保留事项差（不统一的部分，用户拍板）

- **嫁娶专属重忌**：天罡日/河魁日（妨翁姑）-25、神号鬼哭 -15、重丧日 -25 等，保留嫁娶事项独立口径；
- **营造专属土煞**：土府/土符 -20、土王用事（动土）-40、红嘴朱雀 -30、天火日 -15 等，保留营造事项独立口径；
- 同名多档项目（克山/扶山/补龙、土王用事拆舍档）不入单一表。

### 3.4 日破时（时辰冲日支）评审复决

初版曾把日破时纳入通用同价组（-10），评审中用户决定：**修造类保留 -20 重扣、不直接禁用**。落地时回归发现：若直接改通配值，评分器本地 `get_checker` 实例化的通用检查器因无 `_std_event` 标注，会使入学/求医/签约的**日级**日破时被错误带成 -20（原值 -10）。最终三路取数设计：

| 路径 | 取值 | 机制 |
|---|---:|---|
| 修造类 8 事项选时（修造/装修/动土/拆舍/入宅/安葬/作灶/安床） | **-20** | SHENSHA_SCORES 表尾「日破时选时口径」7 条逐事项条目，`_hour_delta` 按规范事项取数 |
| 通用事项日级（入学/求医/签约/未知事项） | **-10** | 逐事项条目与 `('*','日破时')` 通配均为 -10，三路结果一致 |
| 嫁娶选时 | 直接禁用（既有语义，未改） | 嫁娶神煞扩展打禁用标志，不参与排序 |

`_std_event` 标注点共 3 处，缺一即错走通配：评分器 L3901、推荐时柱 `build_checker` 三分支、主程序日课详情 L6126（本次补）。
